# 5. sqlc for database access, not an ORM

Date: 2026-11-02 · Status: Accepted · Epic 1

## Context

The core of this system is concurrency control: uniqueness constraints, conditional updates, `SELECT ... FOR UPDATE`. That requires exact control over the SQL that runs. An ORM hides it, and hand-written `Scan` code is repetitive and easy to get wrong.

## Decision

Write SQL by hand in each service's `queries.sql`, and generate typed Go from it with sqlc. The generated packages (`eventdb`, `bookingdb`) are committed. Each service wraps them in a `Store` with its own API types, so a schema change can't silently change the API. sqlc is pinned with the `tool` directive in `go.mod` and run with `go tool sqlc`.

Rejected: GORM or another ORM, which hides the SQL. Also rejected: plain pgx with hand-written scanning, which has no type checking against the schema.

## Consequences

- \+ The SQL is exactly what runs. Mistakes in queries or types fail at generation time, not at runtime.
- \+ CI runs `sqlc diff`, so generated code can't drift from the SQL.
- − Dynamic queries (optional filters, such as the AI 1 search) are awkward in sqlc and may need hand-written SQL for that one case.

**Reopen if:** most new queries turn out to be dynamic.
